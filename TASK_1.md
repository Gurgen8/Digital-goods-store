# Описание проекта: Тестовое задание 1 (Магазин цифровых товаров)

Это первое тестовое задание, которое включало в себя разработку витрины, защиту от гонок, обработку сбоев и механику промокодов. Ниже подробно описано, как реализован каждый из этапов задания.

## Этап 1. Витрина + базовый флоу выдачи

Была поставлена задача создать витрину магазина по макету и реализовать надежный флоу покупки товара с автоматической выдачей ключа активации со склада. Главное условие — **один ключ ни при каких обстоятельствах не должен уйти в два заказа**.

**Что было реализовано:**
- Сверстаны структурно близко к макету: шапка, баннер-карусель, иконки сервисов, блок пополнения Steam, карточки товаров с интерактивными эффектами (hover).
- Выпадающее меню "Каталог" работает по клику.
- Создан полноценный REST API на NestJS и PostgreSQL (TypeORM).
- Реализован флоу заказа: `created` -> `paid` -> `delivering` -> `delivered`.
- Оплата эмулируется через вебхук-заглушку.

**Защита выдачи ключей:** 
Для того чтобы один ключ гарантированно не ушел двум покупателям, применена **пессимистичная блокировка БД**. При поиске свободного ключа на складе мы используем запрос с `FOR UPDATE SKIP LOCKED`. Транзакция захватывает ровно 1 ключ, меняет его статус на `used` и привязывает к `orderId`. Параллельный запрос проигнорирует заблокированную строку и возьмет следующий ключ. Это на 100% исключает дублирование.

## Этап 2. Однократная выдача под гонками (Race Conditions)

Система должна гарантировать, что при двойных кликах, дублирующихся вебхуках или одновременных вебхуках по одному заказу ключ выдается строго один раз без задвоений и без падения приложения.

**Что было реализовано:**
1. **Защита от двойного клика (Idempotency при создании заказа):**
   - Метод создания заказа (`POST /api/orders`) обрабатывает уникальное ограничение базы данных (Unique Constraint Violation `23505`). Если два параллельных запроса пытаются создать заказ с одним и тем же ключом идемпотентности, второй запрос корректно перехватывает ошибку, читает уже созданный заказ и возвращает его ID (вместо падения с HTTP 500).
2. **Защита от параллельных вебхуков:**
   - Вебхуки с одинаковым `event_id` отбиваются на уровне БД через Unique индекс.
   - Если приходят два разных вебхука на **один и тот же** заказ, метод обработки и выдачи ключа (`startDelivery`) запускается в **строгой транзакции с пессимистичной блокировкой** (`pessimistic_write` на `OrderEntity`). Это исключает параллельный запуск логики выдачи и списания инвентаря.
3. **Двое покупателей одновременно берут последний товар:**
   - Когда клиент нажимает кнопку "Оплатить", сервер находит свободный ключ и накладывает `pessimistic_write` + `skip_locked`. Если два человека нажмут кнопку одновременно, транзакция захватит 1 ключ для первого, а второму моментально вернет `409 Conflict` (Товар только что раскупили). Оплата у проигравших не инициируется.

**Как проверить (Нагрузочное тестирование):**
- **Тест создания заказов и вебхуков:** `pnpm -C apps/backend exec tsx scripts/race-test.ts` (пускает 5 одновременных `POST /api/orders` и 10 одновременных вебхуков).
- **Тест конкурентной оплаты последнего товара:** `pnpm -C apps/backend exec tsx scripts/race-payment.ts` (5 одновременных оплат). Установите остаток товара в БД = 1 и посмотрите, как 4 из 5 запросов корректно отобьются сервером.

## Этап 3. Сбои и восстановление

Реализована обработка ситуаций, когда клиент успешно оплатил товар, но ключи на складе внезапно закончились (или поставщик/БД зависли). Система гарантирует, что заказ не "потеряется" и приложение не упадет.

**Что было реализовано:**
- **Восстановимое состояние заказа:** Если при выдаче ключа инвентарь пуст, заказ переходит в статус `out_of_stock`. Если провайдеры недоступны (таймаут/ошибка) — в `delivery_failed`. Для пользователя покупка не падает с ошибкой 500, а корректно отображает задержку выдачи.
- **Админский интерфейс (Фронтенд):** По адресу `/admin` (или клик по аватарке) доступен список всех заказов в статусе "оплачен, но не выдан" (`out_of_stock` или `delivery_failed`).
- **Безопасная ручная выдача (Идемпотентный Retry):** Добавлен эндпоинт для ручной повторной выдачи ключа после пополнения склада. Перезапуск строго **идемпотентен**: даже если нажать кнопку 5 раз подряд, пессимистичная блокировка пропустит только первый запрос.

## Этап 4. Новая механика с нуля: Промокоды

Реализована механика промокодов. Главный фокус — строгая серверная валидация и защита лимита использований при параллельных запросах.

**Что было реализовано:**
- **Абсолютное недоверие клиенту:** Фронтенд передает только текстовую строку промокода. Вся логика вычисления скидки происходит на сервере.
- **Лимит использований под высокой нагрузкой:** Каждый промокод имеет свой лимит `maxUses`. Метод применения промокода обернут в **двойную пессимистичную блокировку** (`pessimistic_write` на саму запись промокода `PromoCodeEntity` и на `OrderEntity`). Если 100 человек одновременно применят промокод с лимитом "3", БД аккуратно выстроит их в очередь: первые 3 получат скидку, остальные 97 получат отказ `409 Conflict`. Лимит никогда не будет превышен.
- **Защита от двойного клика:** Блокировка заказа предотвращает "сжигание" лимита промокода, если человек нажмет "Применить" 5 раз подряд.

**Как проверить (Нагрузочное тестирование):**
- Скрипт `pnpm -C apps/backend exec tsx scripts/race-promo.ts` бьет по серверу параллельными запросами. 
- **Тест 1:** 10 разных заказов одновременно применяют промокод с лимитом = 3. Скрипт докажет, что ровно 3 запроса вернули успех, а 7 — ошибку `409 Conflict`.
- **Тест 2:** 5 одновременных кликов "Применить" по одному и тому же заказу с кодом "Один раз" (лимит = 1). Скрипт докажет, что применится только один запрос.

## 🛠 Сводка: Скрипты для нагрузочного тестирования (Race Conditions)

Чтобы проверяющим было удобно тестировать отказоустойчивость системы под нагрузкой, мы вынесли все состязательные сценарии в отдельные скрипты. Запускать их нужно из корня проекта.

**1. Тест защиты от параллельных вебхуков и двойных кликов (Этап 2)**
```bash
pnpm -C apps/backend exec tsx scripts/race-test.ts
```
*Что делает:* Пускает 5 параллельных запросов на создание заказа (дабл-клик) + 10 одновременных вебхуков (5 дублей + 5 разных) на один заказ. Доказывает, что заказ создастся 1 раз, и будет выдан ровно 1 ключ.

**2. Тест конкурентной оплаты (Два покупателя на 1 товар) (Этап 2)**
```bash
pnpm -C apps/backend exec tsx scripts/race-payment.ts
```
*Что делает:* Имитирует 5 разных людей, которые пытаются купить один и тот же товар в одну миллисекунду. Позволяет проверить пессимистичную блокировку базы при ограниченном запасе товара (например, если на складе осталась 1 штука, 1 запрос вернет успех, 4 вернут `409 Conflict`).

**3. Тест лимитов промокодов (Этап 4)**
```bash
pnpm -C apps/backend exec tsx scripts/race-promo.ts
```
*Что делает:* Имитирует ситуацию, когда 10 независимых заказов пытаются применить промокод с остатком всего 3 применения, а также 5 одновременных кликов "Применить" по одному заказу. Доказывает, что лимиты строго соблюдаются даже под высокой нагрузкой.
