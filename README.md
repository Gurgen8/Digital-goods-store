# Тестовое задание: Магазин цифровых товаров (Монорепозиторий)

## Описание проекта (Этап 1)

В рамках первого этапа была успешно реализована витрина магазина и базовый флоу покупки товара с автоматической выдачей уникального ключа.

### Что было сделано:
1. **Верстка витрины (Frontend)**:
   - Сверстаны: шапка (Header), главный баннер-карусель (Hero), полоса иконок преимуществ, блок конвертера/пополнения Steam и 3 ряда карточек товаров (Популярные, Рекомендованные, Другие).
   - Адаптивный дизайн (Responsive): корректно работает на всех брейкпоинтах (от мобильных 560px до десктопа 1280px+).
   - Футер и отзывы были пропущены согласно ТЗ.
2. **Флоу покупки (Backend + Frontend)**:
   - Создание заказа (`POST /api/orders`) со статусом `created`.
   - Заглушка оплаты (Мок-вебхук), симулирующая успешную транзакцию.
   - Выдача ключа активации со склада (пул инвентаря).
   - Страница успешного статуса заказа, где отображается купленный товар и сам ключ.
3. **Безопасность выдачи (Конкурентность)**:
   - Реализована строгая привязка "Один ключ — один заказ".
   - Использована пессимистичная блокировка на уровне базы данных PostgreSQL (`pessimistic_write` + `skip_locked`), что на 100% исключает выдачу одного и того же ключа двум клиентам при одновременной покупке.
4. **Конфигурация (Environment)**:
   - Внедрен единый глобальный файл `.env` в корне проекта. И фронтенд, и бекенд берут настройки исключительно из него.
5. **Данные**:
   - Рабочий флоу покупки изначально требовался только для одного товара, но в качестве бонуса инвентарь (ключи) сгенерирован для **первых 4-х товаров**. Остальные товары симулируют ошибку "нет в наличии" (`failed`), чтобы продемонстрировать обработку отказов.

## Описание проекта (Этап 2: Защита от гонок / Race Conditions)

В рамках второго этапа была полностью решена сложная задача обеспечения консистентности при параллельных запросах (Double clicks, Webhook duplication, Simultaneous events). Система гарантирует, что заказ создастся один раз, и ключ будет выдан ровно один раз без задвоений и падений с 500-й ошибкой.

### Что было реализовано:
1. **Защита от двойного клика (Idempotency при создании заказа):**
   - Метод создания заказа (`POST /api/orders`) обрабатывает уникальное ограничение базы данных (Unique Constraint Violation `23505`). Если два параллельных запроса пытаются создать заказ с одним и тем же ключом идемпотентности, второй запрос корректно перехватывает ошибку, читает уже созданный заказ и возвращает его ID (вместо падения с HTTP 500).
2. **Защита от параллельных вебхуков:**
   - Вебхуки с одинаковым `event_id` отбиваются на уровне БД через Unique индекс.
   - Если приходят два разных вебхука на **один и тот же** заказ, метод обработки и выдачи ключа (`startDelivery`) запускается в **строгой транзакции с пессимистичной блокировкой** (`pessimistic_write` на `OrderEntity`). Это исключает параллельный запуск логики выдачи и списания инвентаря.
3. **Скрипт нагрузочного тестирования:**
   - Написан скрипт для эмуляции агрессивных race conditions. Он пускает 5 одновременных `POST /api/orders` (дабл-клик) и 10 одновременных вебхуков (5 дублей + 5 разных) на один заказ.
   - Скрипт подтверждает, что система выживает, возвращает правильные статусы и выдает ровно **один ключ**.

**Как запустить тест параллельных запросов:**
```bash
pnpm -C apps/backend exec tsx scripts/race-test.ts
```

## Описание проекта (Этап 3: Сбои и восстановление)

В рамках третьего этапа реализована надежная обработка ситуаций, когда клиент успешно оплатил товар, но ключи на складе внезапно закончились (или сервис выдачи упал по таймауту). Система гарантирует, что заказ не "потеряется" и приложение не упадет.

### Что было реализовано:
1. **Восстановимое состояние заказа:**
   - Если при выдаче ключа инвентарь пуст (`out_of_stock`) или все провайдеры недоступны (`delivery_failed`), заказ переходит в соответствующий статус. При этом для пользователя покупка не выглядит как ошибка 500 — интерфейс корректно отражает задержку выдачи.
2. **Админский список проблемных заказов:**
   - Создан API-эндпоинт `GET /api/admin/recovery-orders`, который возвращает список всех заказов в статусе "оплачен, но не выдан" (`out_of_stock` или `delivery_failed`).
3. **Безопасная ручная выдача (Идемпотентный Retry):**
   - Добавлен эндпоинт `POST /api/admin/orders/:id/retry-delivery` для ручной повторной выдачи ключа после пополнения склада.
   - **Важно:** Ручной перезапуск выдачи строго **идемпотентен**! Если администратор (или скрипт) вызовет эндпоинт 5 раз подряд, транзакция с пессимистичной блокировкой (`pessimistic_write`) моментально заблокирует заказ на первом запросе, а остальные 4 запроса увидят статус `delivering` и отменятся без последствий.

### 🛠 Как проверить Этап 3 (Тестирование):
1. **Создайте дефицит:** На витрине нажмите "Купить" на любом товаре, кроме первых четырех (например, *PlayStation Plus* или *TikTok Coins*). Для этих товаров на складе (в БД) **нет ключей**.
2. **Убедитесь, что нет краша:** Заказ создастся, оплата пройдет, но статус плавно перейдет в `out_of_stock` (Нет в наличии). Приложение не упадет.
3. **Зайдите в Админку (Frontend):** 
   - Вы можете попасть туда, **кликнув на аватарку** в правом верхнем углу шапки сайта (Header), либо перейдя по URL: [http://localhost:5173/admin](http://localhost:5173/admin)
   - Это специальная страница, созданная для Этапа 3. Там выведен список всех заказов, которые застряли (оплачены, но ключи кончились). Вы увидите ваш проблемный заказ и кнопку "Повторить выдачу" (Retry).
4. **Пополните склад:** Зайдите в базу данных (PostgreSQL) и добавьте одну строчку в таблицу `inventory` (укажите `sku` нужного товара и статус `available`).
5. **Выдайте ключ вручную:** Прямо в интерфейсе Админки нажмите кнопку **"Повторить выдачу"** напротив заказа. Заказ безопасно заберет новый ключ со склада, статус в админке исчезнет, а если обновить страницу самого заказа — там появится заветный ключ!

## Описание проекта (Этап 4: Механика Промокодов)

В рамках четвертого этапа с нуля реализована механика промокодов. Главный фокус — строгая серверная валидация и железобетонная защита лимита использований при параллельных запросах (Race Conditions).

### Что было реализовано:
1. **Абсолютное недоверие клиенту:**
   - Клиент (фронтенд) передает только текстовую строку промокода. Вся логика вычисления финальной цены (в процентах или фиксированной сумме) происходит исключительно на сервере (`orders.service.ts`). Изменить итоговую скидку со стороны клиента невозможно.
2. **Лимит использований под высокой нагрузкой:**
   - Каждый промокод имеет свой лимит `maxUses`. 
   - Метод применения промокода (`applyPromo`) обернут в **двойную пессимистичную блокировку** (`pessimistic_write` на саму запись промокода `PromoCodeEntity` и на сам заказ `OrderEntity`).
   - Если 100 человек одновременно попробуют применить промокод с лимитом "3", БД аккуратно выстроит их в очередь: первые трое получат скидку (статус 201), остальные 97 получат жесткий отказ `409 Conflict` (лимит исчерпан). Ни одной лишней активации не произойдет.
3. **Защита от двойного клика:**
   - Блокировка заказа (`OrderEntity`) предотвращает "сжигание" лимита промокода, если один и тот же человек с нетерпением нажмет кнопку "Применить" 5 раз подряд.

### 🛠 Как проверить Этап 4 (Тестирование):

**1. Тест через UI (Фронтенд):**
- Добавьте любой товар в корзину (нажмите "Купить").
- На странице заказа введите промокод **`WELCOME10`** (скидка 10%). Сервер пересчитает цену. 
- Попробуйте применить код повторно или применить другой код — сервер запретит модификацию.

**2. Нагрузочное тестирование (Тест на Race Conditions):**
Специально для этого этапа написан стресс-тест. Скрипт бьет по серверу параллельными запросами, чтобы попытаться "пробить" лимит.
```bash
pnpm -C apps/backend exec tsx scripts/race-promo.ts
```
**Сценарии скрипта:**
- **Тест 1:** 10 разных заказов одновременно применяют промокод `LIMIT3` (у которого в базе лимит = 3). Скрипт проверит, что ровно 3 запроса вернули успех, а 7 — ошибку `409 Conflict`.
- **Тест 2:** 5 одновременных кликов "Применить" по *одному и тому же заказу* с кодом `ONCEONLY` (лимит = 1). Скрипт докажет, что применится только один запрос.

## Как запустить проект (Локально)

### 1. Переменные окружения
Скопируйте пример конфига в рабочий файл `.env` в корне проекта:
```bash
cp .env.example .env
```
*(В файле уже прописаны все нужные настройки для базы и портов)*

### 2. Запуск базы данных
Для работы бекенда потребуется PostgreSQL. Проще всего запустить её через Docker:
```bash
docker-compose up -d postgres
```

### 3. Установка зависимостей
Установите все модули монорепозитория:
```bash
pnpm install
```

### 4. Запуск серверов (Бекенд + Фронтенд)
Эта команда поднимет оба проекта одновременно в режиме watch:
```bash
pnpm dev
```
*(При первом запуске бекенд автоматически создаст таблицы в базе данных и заполнит их товарами и ключами для тестов).*

## Доступные URL-адреса

- **Фронтенд (Витрина)**: [http://localhost:5173](http://localhost:5173)

### Основные API-эндпоинты:
- `GET /api/products` — список товаров.
- `POST /api/orders` — создание заказа.
- `GET /api/orders/:id` — получение статуса заказа.
- `POST /api/orders/:id/pay` — имитация успешной/неуспешной оплаты.
- `POST /api/webhook/payment` — вебхук для обработки статусов платежей.
